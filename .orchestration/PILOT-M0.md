# Pilot: Research MCP v2 milestone M0 through the ECC orchestrator

The first real workload for the orchestrator. It builds the v2 foundation (milestone M0, 16 work units from [LLD v2 section 12.3](../docs/design/LLD-v2.md)), with Claude and Codex as authors and an agent team reviewing, verifying and merging each unit ([TEAM-DELIVERY-v2](../../agent-control-plane-infra/docs/specs/TEAM-DELIVERY-v2.md)): reviewer and verifier roles rotate across Claude, Codex, Gemini, Kimi and Groq, and agents approve the merges (`team.json`).

| File | Purpose |
|---|---|
| `config.yaml` | Repository policy (JSON-compatible YAML): Claude and Codex author (`author_providers`); all five providers may review; high-risk paths, budgets, model aliases and API model preferences. |
| `team.json` | The agent team: merge approval by agents, role panels, contract paths for the architect, UI paths for the designer. |
| `plan-m0.json` | The 16 M0 work units, with scope, dependencies, acceptance commands and test IDs. Generated by `tools/gen_m0_plan.py` from the LLD and the test plan. |
| `ecc.json` | Operator config: this repository, the weekly certification summary, the API model catalog snapshot, and the `unit-tests` repo check. |

Run every command on the Mac. Below, `ecc` means `~/Documents/GitHub/openclaw-ecc-orchestrator/bin/ecc`, and every `ecc` command takes `--config ~/Documents/GitHub/my-research-mcp/.orchestration/ecc.json`. These shell functions save typing; `with-keychain-secrets` hands the Gemini, Groq and Kimi keys from the Keychain to `ecc` for the team roles:

```sh
ecc() { ~/Documents/GitHub/openclaw-ecc-orchestrator/bin/with-keychain-secrets ~/Documents/GitHub/openclaw-ecc-orchestrator/bin/ecc "$@" --config ~/Documents/GitHub/my-research-mcp/.orchestration/ecc.json; }
decide() { ~/Documents/GitHub/openclaw-ecc-orchestrator/bin/ecc-decide "$@"; }
```

## Expected routing

The orchestrator's classifier was run against this plan and policy with Claude and Codex certified. Tiers: 1 is standard, 2 is advanced.

| Units | Author | Reviewer family | Why |
|---|---|---|---|
| M0-02, M0-03, M0-04, M0-10, M0-11, M0-12, M0-16 (tier 1) | Codex (`gpt-6-astra`) | Claude | Pure functions, settings, adapters and CLI. |
| M0-01, M0-05 to M0-09, M0-13 to M0-15 (tier 2) | Claude (Opus) | Codex | Signals for secrets, security tests, the database, concurrency or architecture. |

Both run on subscriptions. `runner_costs` in the policy only steers the split.

## 1. Preflight (once)

1. **Tools on PATH.** Check `uv --version`, `node --version` (22 or newer), `claude --version` and `codex --version`. `claude` must be **2.1.281 or newer** (nvm's install): older versions reject `--permission-prompts`, which is how the first attempt (run `rmcp-m0`, 2026-10-19) failed in under a second. If `which -a claude` lists an older copy first, put nvm's first for this terminal: `export PATH="$(dirname "$(nvm which default)"):$PATH"`. That copy must also be **signed in**: the second attempt (run `rmcp-m0b`) failed with "Not logged in". Run `claude` once from the same terminal, use `/login`, then exit.
2. **Codex models.** Run `codex debug models` and confirm that `gpt-6-astra` is listed. If it isn't, change `cli_models.codex.standard` and `.advanced` in `config.yaml` **before** step 2, because the policy is copied into the run when the run is created.
3. **Certification.** Run `ecc doctor` and confirm that `cert-latest.json` shows Claude and Codex certified and unexpired. If it has expired, run `launchctl kickstart -k "gui/$(id -u)/local.openclaw-ecc-orchestrator.recertify"` and wait for the notification.
4. **Inbox processor.** Confirm it is running: `launchctl print "gui/$(id -u)/local.openclaw-ecc-orchestrator.inbox-processor" | grep state`.
5. **This repository.** It must be clean and committed on `main`, at `~/Documents/GitHub/my-research-mcp` (renamed from `my-research-mcp-v2` on 2026-10-19; run `git worktree repair` there once after the rename).
6. **Generated files.** Run `python3 tools/gen_test_plan.py --check && python3 tools/gen_m0_plan.py --check`. Both must exit 0.
7. **Model catalog.** Run `ecc catalog-refresh`. Gemini, Groq and Kimi must report `ok`; the team roles on those providers resolve their models from this snapshot. Refresh it when the weekly certification runs.
8. **Round trip.** Run `ecc preflight`. Claude and Codex must both pass: each writes, commits, runs the gate commands and writes a valid handoff in a throwaway worktree through the exact path a unit uses.

## 2. Create the run

```sh
cd ~/Documents/GitHub/my-research-mcp
ecc create-run --run-id rmcp-m0f --plan .orchestration/plan-m0.json
ecc status --run-id rmcp-m0f
```

`create-run` shows the plan and asks you to type `yes`. Afterward only M0-01 is `ready`.

## 3. For each ready unit

Waves follow the dependencies:

1. M0-01
2. M0-02, M0-04 (in parallel)
3. M0-03, M0-05 (in parallel)
4. M0-06, M0-08 (in parallel)
5. M0-07
6. M0-09
7. M0-10, M0-11, M0-12, M0-13 (in parallel)
8. M0-14
9. M0-15
10. M0-16

Scopes don't overlap, so the units in one wave can be dispatched from separate terminals.

1. **Dispatch.** Run `ecc dispatch --run-id rmcp-m0f --unit M0-01` and confirm the plan. When the runner finishes, the orchestrator runs the unit's acceptance commands and the `unit-tests` check. The unit becomes `reviewing`, or goes back to `ready` with a failure brief (the repair loop): dispatch it again. A unit that cannot be retried (not signed in, budget spent) goes to `needs_user` with the fix in `ecc status`.
2. **Team review.** Run `ecc team-review --run-id rmcp-m0f --unit M0-01`. The PR reviewer (plus the security reviewer, architect or designer when the diff calls for them) and then the QA verifier run, each on a provider other than the author's, rotating. If all approve, the agents approve the merge, the queue re-runs the gates on the merged result and merges into `main`. Changes requested or a failed verification send the unit back to `ready` with the findings: dispatch it again.
3. **Clean up** a merged unit's worktree: `ecc cleanup --run-id rmcp-m0f --unit M0-01`.

`ecc drive` (build step 4) will run this loop for the whole milestone with one command.

## 4. Exit (milestone M0)

M0 is done when all of these hold:

- Every unit is `merged`.
- Full `tools/ci.sh` (coverage gate, build, `--help`) passes on `main`.
- Every M0 test in TEST-PLAN Appendix A passes.
- The owner checks pass:
  - **OC-01:** `research-mcp install`, then `research-mcp doctor`, then a client searches three sources through the shim.
  - **OC-02:** Keychain prompts are answered once.

## 5. What to record for the pilot report

For each unit, record:

- author runner and model
- attempts and escalations
- review verdicts
- time from dispatch to merge
- any manual intervention

`ecc status --run-id rmcp-m0f --json` and `ecc events tail --run-id rmcp-m0f` have most of these.

## Safety

- Nothing here pushes. There is no remote, and the policy blocks `git push`, `security` and `launchctl` commands.
- Runners never get credentials. Every external system is faked, and tests run with the network blocked.
- v1 (`my-research-mcp-server`) and `~/arxiv-papers` are never touched.
- Merges change only this repository's `main`.
